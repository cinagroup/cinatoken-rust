# Source Provider And Channel Canonical Matrix

Date: 2026-06-25

Status: canonical, source-derived ground truth for the Go `cinatoken` provider
surface. This is the single reference that the family-level matrices in
`docs/production-readiness-matrices.md` (Provider And Channel Matrix) and
`docs/route-provider-parity-runbook.md` (Provider Smoke Matrix) must agree with.
Where those family tables and this table disagree, **this table is
authoritative** because it is generated by reading the actual dispatch code.

## Source Of Truth

Derived by reading, in `C:\cinagroup\cinatoken`:

- `constant/channel.go` — `ChannelType*` enum, `ChannelBaseURLs`, `ChannelTypeNames`.
- `constant/api_type.go` — `APIType*` enum.
- `common/api_type.go` — `ChannelType2APIType(channelType)` mapping.
- `relay/relay_adaptor.go` — `GetAdaptor(apiType)` (text) and
  `GetTaskAdaptor(platform)` (async media task).
- `relay/channel/*` — per-provider adapter packages.

Dispatch chain for text relay:

```text
channel.type  --ChannelType2APIType-->  apiType  --GetAdaptor-->  channel.Adaptor
```

Async media task relay uses a separate chain:

```text
channel.type / platform  --GetTaskAdaptor-->  channel.TaskAdaptor
```

A channel type that is **not** present in the `ChannelType2APIType` switch falls
back to `(APITypeOpenAI, false)` and is therefore served by the generic
`openai.Adaptor`. This fallback is the reason several "custom/proxy" channel
types are OpenAI-shaped without an explicit case.

## Findings (read before planning provider waves)

1. **Channel type 21 (AIProxyLibrary) has no working text adaptor.**
   `ChannelType2APIType(21) = APITypeAIProxyLibrary`, but `GetAdaptor` has no
   case for `APITypeAIProxyLibrary`, so it returns `nil`. This channel type is
   effectively dead for text relay in Go today. Rust must mark it
   `Unsupported`/`Deferred`, not implement a new adapter, unless the Go behavior
   is intentionally revived first.

2. **Channel type 25 (Moonshot) is a dual-protocol bridge, not plain
   OpenAI-compatible.** Its adapter delegates `ConvertClaudeRequest` to the
   Claude adapter (`relay/channel/moonshot/adaptor.go`), and `relay_adaptor.go`
   comments "Moonshot uses Claude API". Filing Moonshot under a generic
   OpenAI-compatible Rust filter loses the Claude-bridge path. Treat it as a
   dedicated adapter with both OpenAI and Claude request conversion.

3. **The generic `openai.Adaptor` serves only these channel types:**
   1, 3 (Azure), 6, 7, 8, 9, 10, 12, 13, 19, 20 (OpenRouter), 22 (FastGPT),
   31 (LingYiWanWu), 47 (Xinference). Channel types 16, 25, 27, 35, 40, 42, 43,
   44, 45, 46, 48, 53 have **dedicated Go adapters**. Several of those dedicated
   adapters are thin OpenAI-shaped wrappers, but each has its own URL/usage/
   error code and therefore needs its own Rust adapter and fixtures — it cannot
   ride the generic OpenAI-compatible filter unverified.

4. **Several channel types are dual text + task.** They have a text adapter via
   `GetAdaptor` and a media-task adapter via `GetTaskAdaptor`: 35 (MiniMax →
   minimax text + hailuo task), 41 (VertexAI → vertex text + task), 45
   (VolcEngine → volcengine text + doubao task), 51 (Jimeng → jimeng text + task),
   plus task-only mappings that reuse OpenAI base URLs (1/55 → sora task).
   Migration must cover both code paths, not just the text one.

5. **Each channel type maps to exactly one adapter.** The current family-level
   matrices double-list 22, 23, 45, 46, and 47 across multiple families. Use the
   `Adapter` column below as the de-duplicated assignment for cutover planning.

## Cutover Families (de-duplicated)

Derived strictly from the `Cutover Family` column above. Each channel type
appears in exactly one primary family. Dual text+task types appear in their text
family and again under D for the task path; this is the only intentional
double-listing, and it reflects two distinct code paths.

- **Family A — first-canary, dedicated low-risk adapters**: 1, 3, 6-10, 12, 13,
  19, 20, 22, 31, 47 (generic `openai`), 14 (Anthropic), 24 (Gemini), 34 (Cohere
  rerank), 38 (Jina rerank), 39 (Cloudflare Workers AI).
- **Family B — dedicated text adapters, mainstream**: 15-18, 23, 25 (dual), 26,
  27, 35 (text), 40, 42-46, 48, 53.
- **Family C — application / self-hosted OpenAI-shaped**: 4 (Ollama), 37 (Dify),
  49 (Coze). (22 and 47 ride the generic `openai` adapter and are grouped in A.)
- **Family D — async media task**: 2, 5, 36, 50, 51, 52, 54, 55, 56, plus the
  task paths of 35/41/45.
- **Family E — complex signing / long-tail / subscription**: 11 (PaLM), 33 (AWS),
  41 (VertexAI text), 57 (Codex).
- **Unsupported**: 21 (AIProxyLibrary — nil adapter in Go).

Note: Family A intentionally splits OpenAI-shaped types that ride the generic
`openai` adapter from dedicated adapters that merely look OpenAI-compatible.
"Looks like OpenAI" is not "served by the OpenAI adapter"; only the latter can
share the generic Rust OpenAI-compatible path without its own fixtures.
